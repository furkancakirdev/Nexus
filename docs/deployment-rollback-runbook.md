# Marlin Nexus — Deployment and Rollback Runbook

> Version: 1.0
> Verified: 2026-09-09
> Status: `PROCEDURE_DOCUMENTED`, `EXECUTION_REQUIRES_APPROVAL`
> Scope: immutable artifact promotion, candidate verification, production cutover, and rollback

## Safety and ownership

- This runbook is an operator procedure, not authorization to deploy.
- A named release owner, technical approver, security approver, and operations approver must be recorded before execution. Current named owners: `TBD`.
- Never place passwords, session secrets, CPM credentials, cookie jars, auth payloads, TLS private keys, or raw environment files in Git, release artifacts, command history, logs, or chat.
- Use a secret manager or host-mounted files with least privilege. The release runner must use pinned SSH host keys, a pinned TLS CA, and key-only SSH authentication.
- The supplied `release_runner.py` functions generate and validate plans; they do not open SSH, execute Compose, alter production, or perform cutover.

## Release inputs and immutable evidence

Before starting, create a release record containing:

- `release_id` matching `[a-z0-9][a-z0-9-]{2,63}`
- 40-character source commit
- build ID and version
- immutable image digest (`sha256:...`)
- SHA-256 artifact digest
- SHA-256 Compose configuration hash
- previous release ID, image digest, and artifact digest for rollback
- CPM database/company metadata (never CPM credentials)
- pinned SSH host key and known-hosts file
- pinned TLS CA file
- approved candidate port, state path, and secret-file paths
- capacity evidence: available, required, and reserved bytes
- approved release risks, if any

`server/releaseManifest.mjs` and `release_runner.py` must reject missing or malformed identity, image, Compose, artifact, CPM, TLS, SSH, or rollback metadata.

## 1. Preflight and change freeze

1. Confirm the change is merged through the protected branch review process and CI is green.
2. Run the repository gates from the release commit:

   ```sh
   npm ci --ignore-scripts
   npm run quality:format
   npm run quality:lint
   npm run quality:typecheck
   npm run quality:secrets
   npm run test:unit
   npm run test:integration
   npm run test:coverage
   npm run quality:audit
   npm run build
   python -m unittest -v release_runner_test.py release_artifact_test.py
   ```

3. Generate the immutable release artifact with `release_artifact.py`; record its SHA-256 and member allowlist.
4. Run release manifest, runner, target-capacity, and rollback-manifest validation. Any blocker stops the release.
5. Confirm a tested backup exists for application state and ledger snapshots. Do not overwrite the live state directory.
6. Announce the change window, monitoring owner, rollback owner, and abort deadline.

## 2. Secure artifact promotion

Use the runner’s `build_secure_transfer_plan` output. Execute only after human review:

1. Verify the local artifact digest.
2. Transfer with `scp` using `StrictHostKeyChecking=yes`, a pinned `UserKnownHostsFile`, `IdentitiesOnly=yes`, and a dedicated SSH key.
3. Verify the remote artifact digest over the same pinned SSH connection.
4. Store the release manifest and transfer evidence outside the application secret directories.
5. Do not copy `.env`, credential files, cookie jars, TLS keys, or raw database exports into the artifact.

The destination must be a versioned release path. Never replace the active release in place before candidate verification.

## 3. Configuration injection

Inject configuration at runtime through the approved deployment secret mechanism:

- Non-secret settings: Compose environment values or an approved configuration file.
- CPM credentials: read-only mounted credential file (`CPM_CREDENTIAL_FILE`); never inline them in Compose or shell arguments.
- Session/admin identity: approved secret-file or secret-manager references.
- TLS: host-mounted public certificate and private key with restricted permissions; private-key contents never enter logs or artifacts.
- Required safety settings include `NEXUS_AUTH_REQUIRED=true`, `CPM_EFFECTIVE_READ_ONLY=true`, a non-default public origin, a required session secret, and a required admin identity hash.
- Secret mounts must be read-only; candidate containers also use a read-only root filesystem, `tmpfs /tmp`, dropped capabilities, and `no-new-privileges` as generated by `build_candidate_compose_override`.

The operator must record only variable names, file paths, permissions, and validation status—not values.

## 4. Isolated candidate deployment

1. Generate the candidate Compose override with `build_candidate_compose_override`.
2. Verify the candidate uses the immutable image digest, a unique container name, a loopback-only non-production port, isolated state path, and no production port collision.
3. Start the candidate only in the isolated environment.
4. Execute the generated `build_candidate_verification_plan` commands using the pinned CA and approved auth payload file. The payload file must be temporary, permission-restricted, and deleted after use.
5. Require all of the following evidence:
   - candidate container running
   - build ID, source commit, and image digest match
   - `/api/health` succeeds with CA validation
   - authenticated login succeeds without logging response cookies or credentials
   - authenticated overview and department-analysis smoke calls succeed
   - readiness/prewarm checks pass or have only explicitly approved blockers
   - authenticated readiness is verified
   - build-info matches the release manifest
   - CPM effective read-only evidence is true
   - required financial parity evidence passes when enabled
6. If any candidate check fails, stop and remove only the candidate resources; do not touch the active service.

## 5. Migration gate

No application migration framework is currently configured, and CPM is contractually read-only. Therefore:

- Do not run ad-hoc `ALTER`, `INSERT`, `UPDATE`, `DELETE`, `MERGE`, or migration scripts against CPM.
- For a future Nexus schema migration, require a versioned, reviewed migration artifact, an isolated rehearsal, backup evidence, forward verification, and an explicit rollback procedure before adding it to this runbook.
- A release that claims a schema change while no approved migration artifact exists is blocked.
- File-backed state changes must use the existing atomic state writers and a verified backup; do not hand-edit `app-state.json` or HR state.

## 6. Cutover and smoke tests

Cutover is permitted only after candidate evidence and release preflight are valid:

1. Persist the release manifest, active image digest, previous release, rollback digest, Compose hash, and artifact digest.
2. Confirm the backup and restore evidence is attached to the release record.
3. Promote the verified immutable image/configuration through the approved deployment mechanism.
4. Do not expose secrets in command output; redact environment dumps and HTTP headers/cookies.
5. Run post-cutover checks:

   ```sh
   curl --fail --silent --show-error --cacert "$NEXUS_TLS_CA_FILE" https://HOST:4318/api/health
   curl --fail --silent --show-error --cacert "$NEXUS_TLS_CA_FILE" https://HOST:4318/
   ```

6. With an approved temporary auth payload and cookie jar, run authenticated overview, department-analysis, build-info, readiness, and one representative read-only data path.
7. Confirm monitoring, logs, correlation IDs, container health, active digest, and error rate for the observation window.
8. Record status codes, build identity, digests, timestamps, and pass/fail results only; never record credentials, cookies, SQL text, or business rows.

## 7. Rollback triggers

Immediately stop traffic/cutover and roll back when any of these occurs:

- health/readiness fails or an unexpected blocker appears;
- active build ID, commit, image digest, or Compose hash differs from the manifest;
- authenticated smoke test fails or authorization boundaries regress;
- CPM read-only evidence is missing or any write-capable permission appears;
- financial parity, data provenance, or reconciliation checks fail;
- error rate, latency, resource usage, or database connection failures breach the approved release threshold;
- TLS/host-key verification fails;
- state backup or rollback manifest is missing;
- security incident, secret exposure, or unexplained data mutation is detected.

Thresholds and observation-window values are release-specific and must be recorded before cutover; current defaults are `TBD`, not an implicit waiver.

## 8. Rollback execution

1. Announce rollback and freeze further changes.
2. Verify the previous release ID and image digest from the persisted rollback manifest; reject a rollback that matches the active digest.
3. Promote the previous immutable artifact using the same pinned SSH/TLS and digest verification process.
4. Restore the previous Compose/configuration manifest without copying secrets into the artifact.
5. Restart only the approved service set through the authorized deployment operator.
6. Run the same health, authenticated smoke, readiness, authorization, and read-only checks as cutover.
7. If application state was changed incompatibly, stop and invoke the approved isolated restore runbook; never overwrite live state from an unverified archive.
8. Record rollback cause, old/new digests, timestamps, checks, owner, and follow-up issue. Do not record secret values or business payloads.
9. Keep the failed release artifact available for forensic review, access-controlled and retention-managed.

## 9. Release record and incident reporting

Attach:

- source/build/image/artifact/Compose identities;
- preflight and capacity results;
- candidate verification output with secrets redacted;
- backup and restore evidence;
- cutover/rollback timestamps and operators;
- health/readiness/smoke results;
- monitoring observation summary;
- deviations, accepted risks, and expiry dates;
- incident ticket if any trigger fired.

Unexpected failures must include the request correlation ID and sanitized diagnostic context. Never attach raw environment dumps, auth headers, cookie jars, SQL statements containing values, or credential files.

## Current implementation boundary

`release_runner.py` and `release_artifact.py` intentionally produce reviewable plans and validation results but do not execute deployment or rollback. This is a deliberate safety boundary. Executable cutover requires a separately approved operator adapter, secret-store integration, named owners, target thresholds, and an isolated rehearsal.

**Release status until those approvals and evidence exist:** `NOT_RELEASE_READY`.
